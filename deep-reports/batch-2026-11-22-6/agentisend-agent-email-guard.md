## 一句话理解
给能发邮件的 AI 代理套上一层保险丝：限制每小时、每天发多少封，拦截重复轰炸，遇到重要或新收件人时必须等人批准，并提供一键让所有代理停发的开关。

## 通俗解释
代理一旦掌握发信工具，重试循环或提示注入就可能把同一封邮件发出几千次，或者把内部信息发给不该收的人。agent-email-guard 的思路是把发信调用包一层：所有决策只有允许、挂起待审批、拒绝三种结果，每次决策都附带稳定的原因标记、一句人话解释和背后的数字证据。

它提供 Node、Python、PHP、Go 四种语言的包，共用一份规范与一致性测试向量，连原因标记和消息都要求逐字节一致，因此一个 Node 服务和一个 Python worker 可以共享同一份预算。核心规则包括：在 60 分钟内对收件人、主题相同且正文相似度不低于 0.85 的近重复邮件从第四封开始拒绝；检测收件人坍塌，即窗口内大量邮件集中到少数邮箱；按小时、日、月设置原子预留的预算；按滑动分钟限制突发；对重要域名、新收件人或自定义规则挂起审批，人工调用 approve 后重新检查再发；还有彻底拒绝的地址黑名单与 pause 熔断。所有未被规则命中的邮件照常发送。

README 也坦白了一个关键限制：这个库运行在代理进程内，代理能控制的代码理论上可以移除它，两个进程各用内存存储时预算也是分开的。要跨进程共享，需要用 Redis 或 Postgres 存储；要在代理无法绕过的地方强制执行，则要用配套的托管 API 适配器。此外还有一份策略文件、命令行校验与检查工具、GitHub Action（PR 新增发信代码却没接护栏时报警）、以及给编码代理安装的安全技能文件。

## 它不是什么
1. 不是邮件服务商或发送引擎，它不负责真正投递，而是包在 nodemailer、SES、Resend、Postmark、SMTP 等客户端前面。
2. 不是不可绕过的强制沙箱，进程内库可被代理自己的代码卸载或改写。
3. 不是内容审核工具，它管的是频率、重复、收件人和审批，不判断邮件正文是否合规。
4. 不是已经广泛验证的基础设施：5 star、0 fork，且 GitHub 发布接口返回 404，没有正式 release。
5. 不是 Resend 官方产品，README 明确说明代理与 Resend 无隶属关系。

## 痛点
- 代理的重试循环可能把一封退款邮件发四千次，造成骚扰与费用损失。
- 提示注入可能诱导代理给重要客户或陌生地址发信，缺乏人在回路的把关。
- 多个进程、多种语言的代理难以共享同一份发信预算。
- 发信防护散落在各服务代码里，无法用一份策略文件统一管理与审计。
- 编码代理写新发信代码时容易忘记加保护，缺少 CI 层面的检查。

## 使用场景
- 给客服、通知或销售类代理的邮件通道加上速率与重复拦截。
- 多语言微服务共用一个发信预算，避免各算各的。
- 需要人工批准才能给 VIP 客户或新地址发信的合规场景。
- 在 CI 中阻止未接护栏的新增发信代码合并。

## 总结
agent-email-guard 把代理发信这件小事做成了一个有明确策略模型的护栏库：限额、速率、重复检测、审批与熔断一应俱全，四种语言共享同一套语义，连原因标记都要求一致，这在同类小项目里相当克制。它的诚实之处在于写明进程内实现的绕过风险，并给出共享存储与托管 API 两条加强路径。不足是项目极新、只有 5 star 且无 release，长期可靠性尚未被社区验证。对正在让代理掌握发信权限的团队，它的设计思路值得一读，落地时建议配合服务端强制。
