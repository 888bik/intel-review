## 一句话理解
Pulsar 给正在运行的多个编码代理装上一套“对讲机加控制台”：它们可以跨工具、跨机器互相发现和发消息，而你能在手机或另一台电脑上实时围观、插话、批准或叫停。

## 通俗解释
如果你同时开着 Claude Code、Codex、OpenCode 几个代理干活，它们彼此是“瞎子”——不知道对面有谁，也没法把“main 分支冻结了”这种信息直接递过去。Pulsar 的做法是给每个代理注入一层薄薄的 MCP 工具，让它们用自然语言就能列出同伴、发消息、等待回复、查看收件箱。它不设中心服务器、不要账号：同一台机器上的代理靠本机通信，不同机器则通过 Tailscale 组成 agent mesh，每台机器都提供同一个 Web 应用。你在手机浏览器打开这个应用，就能看到所有机器、项目和代理的状态，点开会话看实时回复、工具调用和代码改动，替代理回答权限询问，或直接结束它这一轮。README 中“Prove Human”一节把权限边界写得很直白：代理永远不能批准自己的动作，所有以你身份执行的操作都要先过 Face ID、Touch ID、Windows Hello 或设备 PIN。

## 它不是什么
1. 不是新的编码代理，它不替代 Claude Code、Codex 或 Cursor，只是让它们能互相说话。
2. 不是需要注册账号的中心化调度平台，README 明确写明没有 Pulsar 服务器、没有账号。
3. 不是单纯的日志聚合或通知转发器，消息会唤醒空闲代理，并带有“来自代理而非用户、不能批准任何事”的标记。
4. 不是无人值守的自动化系统，推翻、停止、提交、推送等动作都要求人类二次确认。
5. 不是仅限单一框架的单机插件，目标是跨 harness、跨机器，但各框架能力并不齐平。

## 痛点
- 多个代理并行时互相看不见，重复改同一个文件、踩同一个坑。
- 想把一条约束同步给所有代理，只能复制粘贴到每个终端窗口。
- 人不在电脑前时，代理卡在权限询问或需要决策的地方就会停摆。
- 远程控制工具往往要装服务端、开端口、做鉴权，配置成本高且信任边界模糊。
- 跨机器的代理更难统一管理，机器之间的消息路由和身份判断容易出错。

## 核心功能（依据 README，注明来源）
- 代理可用 list_agents、send、respond、wait、inbox、set_identity 六个工具，按名称、选择器或星号群发，并自动标注来自代理、无法批准（来源：README Use it）。
- 代理被打上 harness、模型、项目、分支、PR 和 GitHub issue 等标签，可用 project=xxx、pr=1402 role=reviewer 这类选择器精确定位（来源：README Use it）。
- agent mesh 基于 Tailscale 把多台机器连起来，开启 HTTPS 证书后同账号设备自动互联，并提供 pulsar doctor --mesh 排错（来源：README Agent mesh）。
- Web 应用可查看会话实时流、回答权限问题、发文件与图片、停止代理、在新 worktree 启动代理、审阅改动后提交推送开 PR、审查 PR 逐行评论（来源：README The app）。
- Prove Human 要求以用户身份执行回答提示、发消息、停止或启动代理、提交推送、上传文件等动作前做生物识别或 PIN 验证，每台机器独立校验（来源：README Prove Human）。
- 安装方式为 npx pulsar setup，会检测已有代理、展示改动并备份所触碰的文件，也提供 npm 与 curl 脚本两种路径（来源：README Install）。
- 提供 CLI 与 REST/MCP 接入能力，可用 pulsar ls、send、ask、interrupt、ui、qr、mesh、doctor 等命令操作（来源：README CLI）。
- 应用内显示 token 用量、按 harness 与模型估算的 API 成本，以及套餐用量 80%、95% 告警（来源：README The app）。
- 安全模型以本机用户账户为信任边界，应用只监听 Tailscale 且只接受你的 Tailscale 身份，README 声明无遥测（来源：README Security）。

## 使用场景
- 同时跑多个编码代理，需要让它们分工、同步约束、避免互相覆盖。
- 代理在多台机器上工作，想在一个界面里统一查看和调度。
- 人离开工位后仍要处理代理抛出的权限询问或方案选择。
- 需要审阅代理改动、逐行评论 PR、控制提交与推送这些敏感动作。
- 关心 token 花费与套餐额度，想把成本摊到每个 harness、模型和日期上看。

## 适用人群
适合同时使用多个 AI 编码代理、并且重视权限边界与可审计性的开发者和技术负责人；对只用一个代理、且不需要跨机协作的人来说，这套网格的搭建与配置成本可能超过收益。

## 注意事项
- 56 star、2026 年 11 月 17 日才创建，v2.0.0 刚发布，社区验证非常有限。
- 跨机器能力依赖 Tailscale 及 HTTPS 证书配置，README 也提示可用自建 headscale 控制服务器，这部分并非开箱即用。
- 各 harness 支持度不一致：Cursor 与 Gemini CLI 不能从应用里回答提示，也不能停止；Codex 用无守护进程模式启动时提示是只读的。
- 信任边界是“你的用户账户”，同机其他进程或拥有你身份的人仍可操作，README 建议读完整安全模型再用于敏感环境。
- README 声称无中心服务器、无账号、无遥测，均属项目自述、未独立核实；真正的安全判断仍需自行审阅代码。

## 总结
Pulsar 抓住了一个正在变普遍的问题：代理多了以后，瓶颈不再是单个代理聪不聪明，而是它们之间怎么沟通、人怎么在环。它把消息路由、跨机互联、远程接管和生物识别确认打包成一套命令行工具加手机应用，设计取舍相当克制——不让代理自我批准、不设中央服务器、每条状态变化都可审计。代价是它很新，跨机部分要配 Tailscale，各框架能力还不对齐。值得关注，但现阶段更适合愿意读源码、能接受早期 API 变动的团队。
