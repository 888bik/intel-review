## 一句话理解
agent-mcts 是一个测试时搜索外壳：它不改写编码代理本身，而是用蒙特卡洛树搜索（MCTS）驱动 Claude Code 这类 CLI 代理，让代理在多个解法和回滚分支之间探索，最后把评分最高的分支合并回你的工作区。

## 通俗解释
常规编码代理是单线的：动手、观察、原地重试，撞到死胡同也没有真正的回退。agent-mcts 借鉴了 SWE-Search（ICLR 2025）的思路并把研究里的 MCTS 搬到了你日常用的代理上。每个搜索节点都是一个独立的 git worktree 加一份分叉出来的代理会话，因此文件内容与对话状态都能分支；值函数默认就是你的测试命令，退出码 0 记 1.0 分，失败则按通过比例给部分分，失败输出还会喂给子节点的修订提示。README 坦率标注了 v0.4 的状态：完整闭环（搜索→实时树→应用）在 Claude Code 上可用，Codex CLI 适配器只对着假的 codex 二进制测过，Kimi 仍在计划中。基准部分也写清了范围：两个任务、一个模型、每组 20 次运行，其中带生成测试的设置在 20 次里有 16 次优于首次尝试、2 次更差，平均提升 4.8 个百分点，约 19 分钟、每次 2.44 美元——这些均为项目自述、未独立核实，不能当作普适结论。

## 它不是什么
1. 它不是新的编码代理或模型：搜索引擎通过薄适配器调用你已有的 claude -p、codex exec 等无头模式。
2. 它不是简单的 best-of-N 多次采样：README 强调是完整的 UCT 选择、扩展、评估、回传流程，预算会向有希望的分支倾斜。
3. 它不是自动提交工具：apply 只是把最佳节点作为普通 squash 合并暂存，最终审查和提交仍由你完成。
4. 它不是经过广谱验证的成熟产品：Codex 仅假二进制测试，Kimi 未实现，基准只有两个任务。
5. 它不是浏览器应用：100% Python，树在终端里实时生长，可随时 Ctrl-C 并在之后 resume。

## 痛点
- 代理第一次给出的方案常常不可用，单线重试缺乏系统性探索与回退。
- 研究论文里的搜索增益停留在研究框架，普通开发者用不上自己手头的代理。
- 并行试多个分支时，工作区状态和会话上下文容易互相污染，难以审计。
- 失败原因很难自动传递给下一次尝试，修订往往靠人肉复读报错。
- 缺乏预算控制与中断恢复，长任务跑一半被打断就前功尽弃。

## 核心功能（依据 README，注明来源）
- UCT 树搜索：通过选择、扩展、评估、回传分配节点预算，而非固定次数重试（来源：README Why、How it works）
- 节点即 git worktree 加分叉会话：文件系统与对话状态同时分支，工作树在用户应用前不受影响（来源：README How it works）
- 测试驱动值函数：退出码与通过率映射到 [0,1]，并支持 --generate-tests 让代理先写测试、--judge 让 LLM 评审 diff（来源：README How it works、Configuration）
- 实时终端 TUI 与 anytime 行为：树实时显示，Ctrl-C 后保存部分树，可用 show/resume 检查与续跑（来源：README Quickstart）
- 适配器架构：Claude Code 原生会话分叉已验证，Codex CLI 用上下文注入（仅假二进制测试），Kimi 计划中（来源：README Supported agents）
- 配置与预算控制：.agent-mcts.toml 可设 agent、测试命令、最大节点数、美元上限、并行度，CLI 参数覆盖文件（来源：README Configuration）
- 可审计记录：每个节点对应 agent-mcts/run/node 分支，状态变化以 append-only jsonl 记录（来源：README How it works）
- 隐藏测试基准：bench/ 目录提供按隐藏测试评分的对照实验与完整报告（来源：README Does it help?）

## 使用场景
- 面对有明确书面规格、可由测试判定对错的任务，让代理探索多条实现路径并择优。
- 在预算上限内并行跑多个节点，比较不同修复思路的通过率与代价。
- 长任务中途中断后，从已保存的部分树继续搜索而不丢失进度。
- 作为 MCTS 研究工具，调整 UCT 常量、值函数与选择策略，在真实软件任务上做测试时搜索实验。
- 为新的 CLI 代理编写 AgentBackend 适配器，复用现成搜索核心。

## 适用人群
适合使用 Claude Code 且任务能自动评判的开发者，以及对测试时搜索、MCTS 在软件工程中的应用感兴趣的研究者。项目由 MCTS 研究者构建并明确定位为研究型工具，愿意接受早期状态和手动配置成本的人更适合；期待开箱即用、想要代理全平台稳定支持的人需要谨慎。

## 注意事项
- Claude Code 是唯一验证过的后端；Codex 仅假二进制测试，Kimi 为 v0.5 计划项。
- 基准只有两个任务、单一模型、每组 20 次运行，且任务都有精确书面规格；提升数字为自述、未独立核实。
- 带 judge 的实验中，评审在 18 次里平均 0 提升，还出现过把 91% 的首次答案换成 68% 的情况，说明评审值函数并不稳定。
- 使用 uv 管理的 Python 项目要在工作树里用 uv run pytest，否则新 worktree 不继承虚拟环境。
- 许可证为 MIT；项目 11 星、1 fork，发布到 v0.4.0，社区验证非常有限。

## 总结
agent-mcts 把「搜索能提升编码代理表现」这一研究结论做成了可接入现有 CLI 代理的实用外壳，工程上几个关键选择很到位：节点即 worktree 保证状态隔离，节点即分支保证可审计，失败输出进入子提示保证反馈闭环，测试作值函数避免主观打分。同时它对自身边界的描述难得地诚实——支持矩阵、基准范围、judge 的失效案例都写出来了。目前它仍是 11 星、单代理验证、两个基准任务的早期项目，适合愿意一起塑造架构的早期采用者和研究者，而非追求稳定产线工具的人。
