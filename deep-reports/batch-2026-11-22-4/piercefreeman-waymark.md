## 一句话理解

它让“后台任务”像写普通代码一样简单：循环、条件、并行分支照常写，编译器把它变成耐久虚拟机的指令，进度存在数据库里，部署或崩了也不重头跑。

## 通俗解释

Temporal 这类工作流引擎用“重放”实现耐久：每一步都从头执行代码、已完成的活动取缓存结果，代价是代码必须确定（不能用 random、datetime.now、副作用）。waymark 走了不同路线：把工作流的源码（如 Python）解析成中间表示（IR），再降级成耐久虚拟机的字节码，Rust 运行时执行字节码并逐步把 VM 状态快照到 Postgres；恢复时字节码从中断处继续，原始代码从不重新执行（来源：README “How It Works”）。这样普通控制流就能写工作流，不需要 DAG/装饰器语法，也不用绕开非确定性 stdlib（编译期会报错让你改成显式 action，来源：README）。作者的理念是：后台任务应该是全栈库的原语，易写、易本地测试、易部署、合理默认即可扩展（来源：README “Philosophy”）。184 star、v0.30.1、94 issue。

## 它不是什么

1. **不是重放式引擎**。与 Temporal/Vercel Workflow 不同，它“compile-once”，代码永不重跑（来源：README “How It Works” 表格）。
2. **不是要求你写 DAG/装饰器**。它强调用普通控制流代码（来源：README “Philosophy”）。
3. **不是追求极致吞吐**。README 明说不打算做到 load performance 最佳，目标是让大多数应用超过 PMF 后还能扩展（来源：README）。
4. **不是只有 Python**。Python SDK 解析 AST，但 IR/字节码设计支持多种语言（来源：README）。
5. **不是成熟稳定**。184 star、94 issue、v0.30.1，仍处于 Project Status 阶段（来源：GitHub）。

## 痛点

- **后台任务易被杀**：临时任务在重部署或 Docker 崩溃时中断；耐久 VM 从快照恢复。
- **重放式代码约束多**：不能用非确定性函数；编译式方案免除。
- **控制流被 DAG 语法限制**：waymark 让循环/条件/并行写成普通代码。
- **本地测试与远程部署割裂**：README 强调两者都要简单（来源：README Philosophy）。

## 核心功能（依据 README，注明来源）

- **编译式耐久执行**：源码 → IR → 字节码 → Rust 运行时，状态快照到 Postgres（来源：README “How It Works”）。
- **Python SDK**：解析 run() 方法的 AST 生成 IR（来源：README）。
- **普通控制流**：循环、条件、并行分支；编译期拒绝非确定性模式（来源：README）。

## 使用场景

- Web 应用里的可靠后台任务（发邮件、数据处理、定时作业）。
- 需要跨机器并行、崩溃可恢复的长流程。
- 厌倦 Temporal 重放约束的团队。

## 适用人群

后端/全栈工程师、需要耐久工作流的应用团队。简单定时任务用不上。

## 总结

waymark 用“编译成耐久虚拟机字节码”绕开了重放式工作流的确定性枷锁，让后台任务回归普通代码，设计思路非常有新意。184 star、94 issue 说明它在活跃迭代但尚未稳定。对受困于 Temporal 约束的团队值得评估。
